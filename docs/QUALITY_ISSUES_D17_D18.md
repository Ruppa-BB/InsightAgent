# D17～D18：质量问题处理与复检

入口：`/data/issues`。质量检查页 `/data/quality` 增加已发布数据版本选择和问题处理入口；检查证据可用 `?check=<检查ID>` 重开。

## 处理方式

1. 完成的检查发现八项硬规则中的违规，就按“数据集＋数据版本＋规则”登记问题。通知阈值不会阻止建单。
2. 同一个未关闭问题重复检出，追加观察事件、样例定位和检查ID，不重复建单。普通检查变为零违规时也不自动关闭。
3. 填写处理说明后开始处理、保存备注，或登记人工豁免。人工豁免表示接受风险，不证明修复，不改变 Agent 的质量门禁。
4. 复检直接读取问题原数据版本，忽略调用方另外选择的版本。系统执行真实质量检查，不接受用户提交的“通过”结论。
5. 原版本最新复检八项硬规则全部通过后，填写说明才能关闭。失败、超时、取消复检不能关闭。复检后又有新观察，原关闭证据失效，必须再复检。
6. 已关闭或豁免的问题再次检出，会产生新问题；重新打开旧问题时不能与现有未关闭问题重复。

本阶段只支持原版本复检。修复原始文件后新导入得到的是另一个版本，不能用其结果伪称旧版本修复；跨版本替代确认尚未实现。系统不会自动修改经营表，处理说明也不会执行为SQL。

## 实现原理

应用 SQLite 迁移6保存问题、不可重复消费的检查标记和追加事件。检查保存与问题观察登记处于同一事务；已有完成检查按时间回填一次。完成或失败的检查快照不能改写。

问题修订号防止并发覆盖。复检开始时登记令牌并释放 SQLite 写锁，再执行 PostgreSQL 只读检查；完成时核对令牌和最新检查ID，防止迟到结果关闭已取消或已有新观察的问题。服务中断留下的进行中复检，可填写原因取消并重新发起。

修复了诊断样例固定引用 `public` 的问题：样例和统计现在使用同一检查连接的版本搜索路径。另外，真实连续导入回归发现暂存表会残留在连接池连接中，现改为 `ON COMMIT DROP`，在提交时自动清理。
