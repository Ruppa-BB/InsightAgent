用户已调整近期顺序：先做六项数据管理扩展，计划20个开发工作日加3～5日缓冲，见 [D阶段每日计划](DATA_MANAGEMENT_PLAN.md)。M2制造业与类帆软扩展暂缓，最终PRD目标保留。以下N1～N10是已完成历史安排，M2～M6为后续参考。

## 最终目标与当前距离

面向制造业/半导体经营分析，形成 **BI Dashboard + AI Copilot + Analysis Workspace**。围绕销售、客户、产品，实现：

数据接入 → 数据质量 → 指标理解 → 问题理解 → 受控动态规划 → SQL/Python 分析 → 异常定位 → 多维贡献 → 可视化与证据 → 保存版本 → 经营报告。

最终主演示：管理者登录 → 看板发现销售异常 → 点击异常进入 Copilot → 比较上月/去年同期 → 客户、产品、区域及客户×产品下钻 → 核验毛利变化 → 查看 SQL/分析过程 → 保存 → 导出中文 PDF。

当前已完成Online Retail II学习版经营闭环：看板、质量/变化提醒、自然语言受控分析、组合贡献与连续下钻、反馈与历史、固定策略预算及快照月报。N10共121项测试通过；N1规则23/28，标准计划执行20/20，仍有5个表达缺口。尚缺制造业成本数据、动态工具规划、多源接入、RAG、权限、可编辑工作台和PDF等最终平台能力。见 [N10验收](ACCEPTANCE_N10.md)。

### 范围与用词

- “个人自学 MVP”描述开发者学习用途；“自学习 Agent”是另一个技术能力，不能从历史保存或缓存推定实现。
- 原 PRD 第34节要求反馈用于评估，第42节将历史案例记忆及跨会话 Memory 放在后续。优先补反馈、评测和经营闭环；案例复用可作为用户关心的后续增强，须单独验收。
- 当前数据是英国零售样本，金额 GBP；不能冒充半导体业务、不含税企业收入或真实毛利。制造业模拟数据应独立、明确标注合成、使用独立单位与口径。
- 贡献分解定位金额变化来源，不证明业务因果；业务假设必须标明依据与不确定性。

## 时间和推进方式

默认单人每天3～5小时，以下 N1～N10 是接下来的10个开发工作日，约30～50小时，考虑学习与返工按2～3个自然周安排。不指定日历日期，避免把周末或尚未投入的时间当作已完成。

每个工作日：理解概念 → 实现小批功能 → 自己运行并解释 → 记录验收与学习笔记。用户已授权助手自主实现；同时保留可讲解的交付批次，不一次引入所有框架。

完成标准以行为与证据为准；未通过的任务先收尾，再顺延。不为满足日期取消查询安全、金额核对或来源记录。

## 经验复用与部署：本地平台之后

用户关心的“自学习”可以先做一个限定案例实验，不必训练模型：反馈 → 人工核验修正 → 版本化案例 → 相似问题检索 → 辅助生成计划 → 与不使用案例的基线比较。

只有批准案例才启用；用户反馈不作为事实、不能直接改SQL/指标或安全规则。检索需按数据源、指标版本和权限隔离；缓存键带案例版本；支持撤回与回滚。离线评测需分开开发集与保留集，检查错误改善、新错误和调用成本。先做1～2周试验，再决定是否扩大；这属于原PRD后续历史记忆方向，不挤占M1主链。

之后按原PRD推进：Docker → 云部署 → CI/CD；再分批安排多租户、多组织、定时同步/报告、通知、ML异常检测、自定义Dashboard、拖拽BI、推荐问题、自然语言改图、Excel导出和完整指标血缘。每批重新估算与验收，不包含在上面的本地平台工期中。Python可编辑执行必须另建隔离执行与资源权限机制。

## 工程、成本与数据约束

- 保持uv/FastAPI/Pydantic/SQLAlchemy/PostgreSQL；现有SQLite应用记录通过迁移逐步统一到应用数据库。引入LangGraph/ECharts/Vue是为满足规划和产品功能，不先堆依赖。
- 当前计划解析缓存不等于PRD要求的查询缓存；后者需数据版本、权限和过期策略。Redis在多进程共享缓存有实际需要时引入。
- 日常回归用模拟模型和固定标准意图；真实模型验收按选定题目小批执行，记录tokens、费用与失败。重试和预算明确，不自动升级昂贵模型。
- 毛利依赖历史成本快照，禁止用随机成本补到真实零售数据后冒充实际经营；无真实企业数据时明确使用模拟制造业样本。
- 每次交付记录需求章节、输入/操作、数据版本、预期、实际、证据、未完成项。新增的工程测试数量不等于业务标准问题数量。
