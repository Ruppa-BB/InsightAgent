# Day 6–14 相关实现：按代码理解 Agent MVP

这份导读记录本次一次性推进的代码。它不是“用户已学完这些天”，也不表示真实模型已验收。建议按下面顺序阅读，每次只改一个小点再运行。

## 1. 从请求校验到查询保护

`tools/schemas.py` 使用 Literal 限定指标/维度，extra=forbid 拒绝未知字段，模型校验器检查日期顺序和 5 个日历年上限。原先 365×5 会误拒闰日，366×5 又偏宽；现在用目标年份的月份天数确定边界。

`db.read_connection()` 开启只读、REPEATABLE READ 事务，并用 set_config 的第三个参数 true 设置事务局部超时。这样一次分析的多条 SQL 看到一致快照。事务结束后设置失效，连接归还连接池。5 秒限制单条语句，不是整个 HTTP 请求的总时间。

`sql_allowlist.py` 只从服务端字典取 SQL 表达式，日期/国家/客户/商品等值单独绑定。请求 limit+1 行用于发现截断，真正返回 limit 行；结果告诉调用者是否截断。无分组的聚合天然只有一行。

旧 `/tools/sales-query` 保留列表响应；新 `/api/query` 返回指标、单位、参数、SQL、截断和来源，更适合 Agent。

## 2. 环比为什么不能只取“上一行”

`sales_mom=(本月-上月)/上月`。缺了 2 月时，3 月不能拿 1 月当上月。`mom_tool.py` 按日历月份走，缺月和零基数返回 null 并说明原因。单月范围必须从该月 1 日到次月 1 日。数据覆盖不完整的月份不能解释为完整月。

## 3. 贡献分解与对账

先分别查两期总销售额，再对两个期间出现过的全部客户/商品/国家聚合。使用稳定编码分组，保留只在一期出现的对象。

每个对象的贡献=本期销售额−基期销售额。对于每一个维度，必须满足：所有对象的基期之和=基期总额，所有对象的本期之和=本期总额。任何不一致就中止结论。客户、商品、国家是三个观察角度，不能互相加起来。

图表只展示各方向前 10 名，但对账使用全部分组，并记录其余对象的变化合计。超过工具容量（10000 组）会报错，不对截断结果归因。去重客户数/订单数跨商品不可简单相加，因此目前只有销售额提供完整贡献分解。

贡献是会计式分解，不是因果推断。“某客户本期没成交”不能直接写成“客户流失”。

## 4. 模型的职责与边界

`agent/provider.py` 提供两种解析器：

- demo：有限句式的规则解析器，页面明确提示，查询的仍是真实数据库。
- openai_compatible：调用配置的模型，要求返回结构化 JSON。

结构化意图包含 action、metric_code、period、previous_period、group_by、filters。模型只能提出计划；它的结果再次通过 Pydantic 校验，不允许携带 SQL。不支持的问题、缺少年份等需澄清。真实模型未配置时不会悄悄退回规则模式。

模型目前不看原始订单或查询结果，最终数值解释由工具结果和固定模板生成。这个实现是有限工具编排，后续可再扩展模型的多轮规划。

## 5. Agent 执行顺序

`agent/service.py` 根据趋势/比较意图选择工具，在一个只读快照中运行元数据、指标查询、必要的贡献查询，核对结果后生成解释。Trace 记录意图、选用工具、SQL/参数和核验状态。执行完成后一次返回，当前没有流式步骤更新。

## 6. 页面与保存

`main.py` 只负责 HTTP 边界，`static/` 提供本地单用户页面。页面中的用户/数据库字符串通过 textContent 写入，不当 HTML 执行。金额 JSON 用字符串保留 Decimal 精度；图表转为 Number 仅用于绘图，精确值保留在表格与导出中。

`agent/store.py` 用 SQLite 保存分析结果，与只读业务 PostgreSQL 分开。会话 ID 查找最近成功的意图，“再看英国”保留日期、指标并增加筛选。新问题可以新建会话。JSON/Markdown 导出包括来源、限制和可复算记录。

## 8. 2026-10-03：接入 DeepSeek 与控制成本

真实模型已接入，默认使用 `deepseek-flash`。模型把自然语言转换成受校验的分析计划，Python 工具执行数据库查询并核对数字。模型不会直接执行 SQL，也不接收原始订单明细。

- API Key 只保存在本机 `.env`，文件由 Git 忽略，前端和日志不输出密钥。
- 关闭 thinking，单次输出上限为 700 tokens；不自动重试或升级模型。上限控制输出长度，不代表每次都会用满。
- 相同问题、相同上下文的有效解析计划缓存一小时；命中缓存时仍重新查询数据库，因此数据不会因计划缓存而冻结。缓存只在当前服务进程内，重启会清空。
- “再看英国”等支持的明确追问由本地逻辑继承上下文，无需再调用模型。
- 返回模型用量，让页面区分真实调用、缓存命中和本地追问。

两次真实请求分别使用 543 和 545 tokens，共 1088 tokens。销售额比较、贡献对账、历史保存均成功；相同问题的缓存命中和英国追问均无新增模型调用。49 个自动测试通过，自动测试中的模型请求使用模拟响应。

页面参考 Simple Analytics，采用白底、珊瑚红强调色、圆角按钮和简洁图表。页面通过 FastAPI 提供静态文件，JavaScript 调用分析 API，并把返回的指标、回答和贡献数据绘制出来。

## 9. N1：建立评测基线

工程测试验证代码行为；业务问题评测验证问题理解及分析正确性，两者分母不能混用。N1使用28个问题，分别检查规则解析、人工标准意图执行、真实模型小样本。独立参考SQL核对金额；固定锚点防止把错误数据库结果直接当新答案。规则23/28、标准执行20/20、真实样本3/3的含义不同，不能合并成准确率。

参考SQL使用参数绑定，空筛选参数显式CAST为text，避免PostgreSQL无法推断NULL类型。评测历史写临时SQLite，业务库只读。运行失败退出码1可以代表被准确检测的能力缺口，不等于程序崩溃。详细记录见 ../evaluation/README.md。

## 10. N2：反馈存储与幂等

分析是事实证据的快照，反馈是用户意见；两者分表保存，按analysis_id关联。Pydantic校验评价枚举和文字长度，API使用PUT保存当前反馈。相同请求反复发送不重复改变状态，称为幂等；修改内容才增加revision。SQLite外键防止孤立关联，写事务保证检查与保存一致。

旧数据无需删除或重导入，新表在首次访问时创建。历史详情读取当前反馈，前端用radio与textarea回显；失败时保留输入并提示。保存反馈不等于训练模型或让Agent自动学习，后续需要核验、评测与受控复用。N2通过66个工程测试及实际浏览器保存/回显验证。

## 11. N3：比值指标与同比

销量按件数相加，客单价按去重订单作分母，加权均价按总件数作分母。SQL用NULLIF把零分母变为NULL，不能把没有数据当成零均价。按组分析比值需重算分子/分母，不能相加或简单平均。同比比较去年同一日历月，先检查完整覆盖，再处理缺月与基期0；闰年不用减365天。页面百分比只用于显示，原比例及SQL证据保留。详细定义见 ../METRICS_N3.md。

## 12. N4/N5：质量与变化提醒

历史清洗排除数量和当前数据库问题是两种统计。取消属于已排除记录的子集，不能重复相加；没有交易的日子不代表漏数据，缺失率必须有预期全集才可计算。月份边界、空月、零基数和质量失败要先判断，再计算环比或移动平均偏离。

移动平均只用之前连续的完整月份，排除未来信息；严格超过配置阈值才提醒。提醒只能说明数值偏离，不证明业务原因，季节性和月份天数仍需后续分析。质量和检测在同一只读事务中执行，保存独立快照，下载不重算。详细公式和证据见 ../QUALITY_ANOMALIES.md。
