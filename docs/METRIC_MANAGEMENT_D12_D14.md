# D12～D14：指标口径与版本管理

2026-10-06完成。入口 `/data/metrics`，也可从分析工作台、资产目录、质量管理、导入批次导航进入。最终目标仍是原PRD的数据分析平台；本阶段完成零售学习MVP的数据治理能力，下一阶段D15～D16为血缘。

## 使用步骤

选择八个已有指标之一，修改名称或业务说明，保存草稿；核对页面固定公式、单位、过滤条件和维度，再发布。草稿不影响计算，发布产生新的不可变版本。取消「启用新计算」并发布即可停用；重新勾选并发布产生启用新版本。

新分析与月报展示实际口径版本链接，点击直接展开对应历史版本。历史记录保存完整定义快照，JSON/Markdown导出包含证据；月报模板为retail-monthly-v3，哈希包含口径快照。旧模板月报不重新渲染。扩展之前的分析显示「历史口径未登记」，不会补造v1证据。

## 原理与实现

- `dm_metric_heads` 保存发布指针、草稿与编辑revision；`dm_metric_versions` 保存(code,version)唯一的发布内容和登记时间。SQLite新增迁移登记4，业务PostgreSQL不修改。
- 首次登记将代码中八个计算模板保存为v1。这个时间是登记时间，不代表历史计算开始时间。
- 编辑与发布用BEGIN IMMEDIATE事务及expected_revision检查；过期提交409，重复同内容草稿不增revision；无草稿无法发布。发布只新增版本并移动指针，不覆盖旧版本。
- 允许字段只有name、description、enabled。Pydantic拒绝额外SQL、公式、单位、维度或任意字段，去掉首尾空白后校验长度。每个metric_code唯一绑定同名formula_key；不能给销售额换上订单数公式。
- 公式、过滤、维度和零分母规则由已有白名单工具执行。当前仅维护八个既有模板，没有新增自定义指标或任意公式编辑器。名称/说明修改不会改变数值。
- 每次计算开始捕获整套已发布定义，ContextVar在嵌套工具间传递快照，finally恢复上下文。执行中有人发布，当前计算仍使用启动版本；后续计算读取新版本。
- 销售查询、同比、环比、总览、异常和指标解析工具读取被固定的定义并检查启用状态。停用被使用指标会明确409；固定六指标总览/月报若包含停用指标会拒绝生成。销售额停用会阻止依赖它的同比/环比工具。异常自身的环比检测规则仍是固定规则，并非sales_mom指标的执行。
- 分析保存实际主指标及同比工具口径，月报保存六指标及嵌套工具证据。父子下钻共同使用的指标若版本变了，拒绝混用并提示开启新分析；切换到父分析未使用的另一指标仍允许。

## API

| 方法和路径 | 用途 |
|---|---|
| GET /api/data/metrics | 发布状态、revision和草稿 |
| GET /api/data/metrics/{code}/versions | 不可变发布历史 |
| PUT /api/data/metrics/{code}/draft | 校验并保存草稿 |
| POST /api/data/metrics/{code}/publish | 原子发布/停用/重新启用 |
| GET /api/metrics | 当前启用指标及既有工具信息 |

`get_metric` 在执行上下文里返回固定版本；脱离执行上下文时仍提供代码中的学习参考模板。需要读取当前管理口径用注册API或resolve_metric工具。资产目录原有指标说明仍是模板参考，当前发布口径以指标管理页面为准。

## 边界

本机单用户手工发布，没有多人审批、发布人身份、权限审计、定时生效或任意计算模板编辑。启用/停用也是版本内容，恢复通过新版本发布。历史快照不因更新而改变，但重新执行旧SQL仍需要对应数据版本可用；不承诺历史数据永远可复算。外部管理员直接改SQLite或修改SQL程序不受页面治理流程保护，未来算法变化需明确新增模板版本迁移。
