# D8～D11：数据导入与批次管理

交付日期：2026-10-06。入口 `/data/imports`，资产目录与分析页均有链接。已完成受控本地零售导入，不是通用ETL平台。

## 使用步骤

1. 将文件放到data/raw；支持Online Retail II约定结构Excel或单份源CSV（原始列名或对应规范列名），不支持任意字段映射、.xls或五张导出表的任意混合上传。
2. 在导入页面登记源文件，保存副本、SHA256、大小及批次ID。同内容文件返回已有批次，不重复登记。
3. 启动隔离导入，通过独立Python进程读取、清洗、导出、创建schema、COPY和核验。页面点击刷新状态，不等待百万行任务完成。
4. 核验通过后发布可选版本；到分析工作台选择新版本。默认仍是原有零售基线，不全局替换。
5. 新分析和新月报保存实际版本、批次ID及源指纹。旧分析/报告保留原快照，旧会话不允许混用其他版本。

源列：Invoice、StockCode、Description、Quantity、InvoiceDate、Price、Customer ID、Country。512 MiB文件预算；原始行数≤150万在读取后检查，这不是进程内存硬限制。首次新增pandas/openpyxl依赖，已记录pyproject与uv.lock。

## 数据管理原理

源文件副本保持登记指纹，执行前重新核对；原始文件后续修改不会影响已登记批次。清洗复用原脚本，并补空编号/国家、非有限值与非整数数量/客户编号检查。金额按数据库4位单价、2位金额、ROUND_HALF_UP计算，汇总用Decimal字符串避免浮点尾差。取消记录包含在invalid_rows，不与之相加；不自动删除疑似重复经营行。

每个批次固定schema名ia_import_加UUID。写入目标只能来自系统生成并校验的schema；不把文件名拼入SQL。建表、临时COPY、插入与八项质量规则、事实/维度计数和金额对账在同个PostgreSQL事务中。失败回滚新schema，不改public；已有schema冲突不自动DROP。

PostgreSQL提交后才登记SQLite可选版本，两个数据库没有分布式事务。若PG已提交但登记失败，新schema不能被正常选择；进入recovery_required需核查，不能自动重写。进程中断/排队超时刷新时提示人工核查；PID检测不是持久任务调度器，当前没有断点续传或自动灾难恢复。

正常失败可重试同一源副本；published重复启动直接返回，不增加尝试次数。恢复状态禁止自动重跑。修正源文件后新指纹形成新批次；相同文件换清洗策略的强制重新版本化尚未提供。

## 元数据与版本

SQLite增量版本3：dm_import_batches（唯一指纹、状态、统计/日志）、dm_dataset_versions（已发布批次与schema映射）。源文件/清洗产物在data/generated/managed_imports中，与原产物隔离且Git忽略。

状态：registered→queued→running→published；正常异常为failed；不确定提交/进程状态为recovery_required。日志保存受控阶段信息和异常类型/SQL状态，不存凭证或原始驱动消息。

请求X-Dataset-Version只允许baseline-v1或已登记发布UUID。ContextVar按请求隔离，SQL连接使用事务局部search_path，只读工具及查询超时仍有效。页面查询期间锁定版本选择，切换开启新会话；父分析或会话版本不一致拒绝执行。API未指定版本继续读public。

版本为不可变导入快照的应用约定，不是数据库防篡改权限或逐行哈希证明；管理员仍可能外部改数据。资产目录当前固定展示原public基线，新版本管理在批次页，尚未提供每个版本独立资产字典。

## 学习知识点与下一步
